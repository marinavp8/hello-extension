Seguridad: componentes e inyección en la pestaña


    

      
1. Modelo de confianza

      
Cada parte tiene un nivel de privilegio distinto. Una extensión se rompe cuando algo con poco privilegio consigue que algo con mucho privilegio actúe en su nombre (el problema del confused deputy).

      

        

          
ComponentePrivilegioConfianza

Content scriptDOM de la web y poco de chrome.* (runtime, storage)Media

            
Código en el mundo MAINNinguno propio, comparte JS con la webNula

2. Mundos aislados (isolated worlds)

      
El content script comparte el DOM con la página, pero no el entorno JavaScript: cada uno tiene su propio window, variables globales y prototipos.

      
    
        
  • La página no puede leer variables del content script ni llamar a sus funciones.
    • 
        
  • El content script no ve las globales de la página.
    • 
        
  • Ambos modifican el mismo árbol DOM, y por ahí pasa el canal de ataque más habitual.
    • 
        
  • Protege a la extensión de que la web sobrescriba Array.prototype.push o JSON.parse.
    • 
      

    


    

      
3. Formas de inyectar código en una pestaña

      
Declarativa, en el manifest:

      
"content_scripts": [{
  "matches": ["https://ejemplo.com/*"],
  "js": ["content.js"],
  "run_at": "document_start",
  "world": "ISOLATED"
}]

      
Programática, con chrome.scripting (permiso scripting más host_permissions o activeTab):

      
await chrome.scripting.executeScript({
  target: { tabId },
  files: ["content.js"],
  world: "ISOLATED"   // o "MAIN"
});

      
Dinámica y persistente: chrome.scripting.registerContentScripts([...]).

      
El parámetro world es la decisión de seguridad más importante. ISOLATED (por defecto) es seguro frente a la web. MAIN corre en el mismo contexto que los scripts de la página, así que cualquier script de la web puede leer, sustituir o secuestrar lo que pongas ahí.

    


    

      
4. Cómo se inyecta un objeto en window de la página

      
Es el patrón de las wallets (como window.ethereum) y de cualquier extensión que expone una API a la web. El objeto debe vivir en el mundo MAIN, porque desde ISOLATED la página no lo vería.

      
Opción moderna (MV3), con world: "MAIN" en el manifest:

      
"content_scripts": [
  { "matches": ["https://*/*"], "js": ["inpage.js"],  "world": "MAIN",     "run_at": "document_start" },
  { "matches": ["https://*/*"], "js": ["content.js"], "world": "ISOLATED", "run_at": "document_start" }
]

      
Opción clásica, insertando un <script> desde el content script:

      
// content.js (ISOLATED)
const s = document.createElement("script");
s.src = chrome.runtime.getURL("inpage.js");
s.onload = () => s.remove();
(document.head || document.documentElement).appendChild(s);

      
inpage.js debe estar en web_accessible_resources. No sirve textContent con páginas de CSP estricta, y MV3 prohíbe código remoto.

      
El puente entre los dos mundos. El objeto inyectado no tiene acceso a chrome.*, así que necesita un puente con postMessage:

      
Página / inpage.js (MAIN)  ⇄  content.js (ISOLATED)  ⇄  service worker
        window.postMessage        chrome.runtime.sendMessage

      
// inpage.js (MAIN)
window.miApi = Object.freeze({
  pedir: (datos) => new Promise((resolve) => {
    const id = crypto.randomUUID();
    const onMsg = (e) => {
      if (e.source !== window || e.data?.target !== "page" || e.data.id !== id) return;
      window.removeEventListener("message", onMsg);
      resolve(e.data.payload);
    };
    window.addEventListener("message", onMsg);
    window.postMessage({ target: "extension", id, datos }, window.location.origin);
  })
});

      
// content.js (ISOLATED)
window.addEventListener("message", async (e) => {
  if (e.source !== window || e.data?.target !== "extension") return;
  const payload = await chrome.runtime.sendMessage({ type: "API_CALL", datos: e.data.datos });
  window.postMessage({ target: "page", id: e.data.id, payload }, window.location.origin);
});

    


    

      
5. Riesgos principales y defensas

      

        

          
El mundo MAIN es territorio hostil

          
    
            
  • Cualquier script de la web (anuncios, librerías de terceros) puede reemplazar o envolver tu objeto. Object.freeze ayuda, pero no garantiza nada.
    • 
            
  • No pongas secretos, tokens ni lógica de autorización en inpage.js. Que sea solo una fachada fina.
    • 
            
  • No confíes en las funciones nativas (JSON, Array, fetch) dentro de MAIN: la página puede haberlas modificado antes que tú.
    • 
          

        

        

          
El puente postMessage se puede falsificar

          
    
            
  • Cualquier script de la web puede enviar mensajes con la misma forma que los tuyos.
    • 
            
  • Valida siempre e.source === window y el formato, y usa un targetOrigin explícito, nunca "*".
    • 
            
  • Trata todo lo que llega como entrada no confiable: valida tipos, longitud y valores permitidos.
    • 
          

        

        

          
Confused deputy en el service worker

          
    
            
  • Si el content script reenvía sin filtrar, la web puede lograr que el service worker, con más permisos, haga cosas por ella.
    • 
            
  • Usa una lista cerrada de acciones (type) y nada genérico del tipo "haz fetch a esta URL".
    • 
            
  • Las acciones sensibles (firmar, pagar, enviar datos) piden confirmación en una interfaz que la web no controle, como un popup o una ventana de la extensión.
    • 
          

          
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (sender.id !== chrome.runtime.id) return;   // solo mi extensión
  if (!sender.tab) return;                       // espera un content script
  const origin = new URL(sender.url).origin;
  if (!ORIGENES_PERMITIDOS.has(origin)) return;
  // ...
});

        

        

          
XSS dentro del content script

          
    
            
  • Nunca uses innerHTML con datos de la página o de la red. Usa textContent o createElement.
    • 
            
  • Para tu propia interfaz inyectada usa Shadow DOM (mode: "closed"), para que estilos y scripts de la web no la alteren.
    • 
          

        

        

          
Superficie extra que añades tú

          
    
            
  • web_accessible_resources: cada archivo listado puede ser cargado por la web y delata que tu extensión está instalada. Limita por matches y lista solo lo imprescindible.
    • 
            
  • externally_connectable: permite que ciertas webs hablen con tu service worker. Úsalo solo con dominios concretos.
    • 
            
  • host_permissions amplios (<all_urls>): si comprometen la extensión, acceden a todo. Mejor activeTab u optional_host_permissions pedidos en el momento.
    • 
          

        

        

          
Defensas que ya trae MV3

          
    
            
  • CSP por defecto: sin eval, sin scripts inline y sin código remoto en las páginas de la extensión.
    • 
            
  • Todo el código va empaquetado y se revisa, sin descargar JS de un servidor.
    • 
          

        

        

          
Datos y cadena de suministro

          
    
            
  • chrome.storage no está cifrado. No guardes contraseñas ni claves privadas en claro. Para datos temporales usa storage.session (en memoria).
    • 
            
  • Fija versiones de dependencias, usa lockfile, ejecuta npm audit y minimiza librerías: una dependencia comprometida corre con los permisos de tu extensión.
    • 
            
  • Activa 2FA en la cuenta de la Chrome Web Store: quien publique una actualización maliciosa llega a todos tus usuarios.
    • 
          

        

      

    


    

      
6. Checklist rápida

      
    
        
  1. Permisos mínimos, y activeTab en lugar de hosts amplios cuando sea posible.
    2. 
        
  2. Content scripts en ISOLATED. Usa MAIN solo para exponer una API fina a la web.
    3. 
        
  3. Un objeto en window solo como fachada, sin secretos ni lógica sensible.
    4. 
        
  4. Valida source, origin y esquema en cada postMessage y runtime.onMessage.
    5. 
        
  5. Lista cerrada de acciones en el service worker y confirmación del usuario para las críticas.
    6. 
        
  6. Sin innerHTML con datos externos, y Shadow DOM para la UI inyectada.
    7. 
        
  7. web_accessible_resources y externally_connectable restringidos por matches.
    8. 
        
  8. Nada sensible en chrome.storage sin cifrar, y dependencias auditadas.
